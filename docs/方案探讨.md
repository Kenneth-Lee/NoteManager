* 平台选择推荐Python，这一点我也赞成。但我希望对比一下用nodejs的优劣。

* rst 的交叉引用问题，我其实觉得是好解决的。我们不是sphinx，所以我们不需要完全符合它的语义。
  为了解释这个问题，让我解释一个基本原理：我们不是生成某个界面，我们是动态维护一个html的目录，
  这个目录都在我们的控制下，我们会为每个rst或者md文件生成一个html文件，而且保持原来的目录结构，
  这样rst中的:doc:或者md中的[xxx](xxx/xxx.md)这种索引，我们都可以直接指向对应的html文件。
  而:ref:我们也不需要生成静态的连接，我们可以变成一个js调用，调用读取我们动态维
  护的“索引到位置”的数据库，直接跳过去。而directive或者role这些不可控的插件，我
  们不支持或者选择有必要的支持就是了，我们是管理这个笔记，不是再做一个sphinx。

* 增量索引的一致性的问题，我觉得不是问题，因为通常我们都是用第三方编辑器编辑文
  件的，比如vim，你是:w的时候才发生一次文件更新，更新的时候重新解释文件，这和你
  默认扫描这个文件时它的格式如何解释的逻辑是一样的，如果里面有错，就是这个文件
  索引不了或者显示有误而已，不影响其他部分的显示，因为每个md或者rst对应的html文
  件都是固定的。

  至于大文件拷入，这个有一段时间需要后台服务进行动态扫描，这是肯定的，我们可以在
  主控服务器上加上状态标记，所以正在扫描，数据不可靠就行了。

* Master/Worker 架构的复杂度问题，我赞成你的意见，我们用一个后台，监控多个目录就行，
  只要保证每个工程的数据都在那个工程内，不会互相影响就行。

* 搜索引擎的选择，我觉得首先要保证如果我把这个html目录拷贝给别人，在有完整浏览器的平台上，也能查询，
  不需要它另外安装python，所以，保证查询能用js来完成，这是核心问题。

* Markdown 链接格式不统一问题，我们先支持一种（比如标准的），以后慢慢根据需求扩展新语法就是了。

* 设计一个webui是个好主意，便于调试和观察是否有问题，但最终我们还是希望我们整个
  笔记，可以把html目录拷贝出去，在任何有浏览器的地方都可以打开，这是最方便的。
