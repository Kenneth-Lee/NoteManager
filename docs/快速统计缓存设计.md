# 快速统计缓存（Scan Manifest）设计说明

## 1. 背景与问题

Daemon 在恢复监控目录时，需要判断「是否要对某个项目执行 `full_build`」。当前实现会在判定阶段调用 `scan_directory()`，对整棵树做一次 **路径 + mtime** 的遍历，以对比 `.NoteManager/status.json` 中记录的 `last_build` 与 `file_count`。

这在工程很大、文件很多时是 **O(文件数)** 的纯磁盘开销。虽然远轻于真正的 `full_build`（渲染与索引），但在「绝大多数启动都没有内容变更」的场景下，仍希望把冷启动的判定成本压到更低、更可预期。

**快速统计缓存**的目标是：在 **不读取文件内容** 的前提下，用一份持久化的小摘要，让多数启动路径只做 **常量级或近常量级** 的读盘，仅在「疑似有变更」时再退回到完整目录扫描。

## 2. 目标与非目标

### 2.1 目标

- 在「源文件未变化」的常见情况下，**跳过**对整棵树的完整枚举（或将其降为一次极小的校验）。
- 摘要文件体积可控（单项目通常数 KB 量级），读写原子、易调试。
- 与现有 `status.json`（构建结果元数据）正交：缓存只服务 **变更检测**，不替代构建产物状态。

### 2.2 非目标

- **不保证**在极端边界情况下零误判；若摘要认为「可能变了」，仍应 **回退到现有完整扫描逻辑**，正确性以全量扫描为准。
- 不替代 watchdog 的 **在线增量更新**；缓存只优化 **冷启动判定**。
- 不在本文档中规定具体哈希算法实现库（实现阶段可选用 `hashlib.sha256` 或更快的非加密摘要算法）。

## 3. 不可能「零遍历」的说明

若要严格判断「任意 `.md/.rst` 是否新增、删除或 mtime 变化」，在 **不依赖 OS 持续事件流** 的前提下，对一般文件系统 **至少需要一次与文件数成比例的信息收集**（列出路径并 `stat`）。

因此「快速统计缓存」并不是魔法式的 O(1) 真相源，而是：

1. **常见快路径**：读一个小摘要 + 极少量元数据，若与磁盘上 **可 O(1) 取得的全局信号** 一致，则 **认为未变**；
2. **疑似变更**：再走完整扫描（与今天等价）。

全局信号需要满足：**任一源文件变更时，该信号以极高概率变化**。实践中可采用 **根摘要（rollup）** 或 **目录级子树摘要（可选优化）**。

## 4. 核心思路：Scan Manifest（扫描摘要）

在每个项目下增加一份仅用于判定的缓存文件，例如：

```text
.NoteManager/scan_manifest.json
```

其语义是：**上一次完成「变更检测所需统计」时的快照**。它与 `status.json` 的关系如下。

| 文件 | 职责 |
|------|------|
| `status.json` | 构建结果元数据：`last_build`、`file_count` 等，面向展示与人工阅读。 |
| `scan_manifest.json` | 冷启动 **快速判定** 用摘要：在实现完整扫描后写入；启动时先读它再走快路径。 |

## 5. 建议字段（Schema）

以下为逻辑字段，实现时可增删，但需带 **版本号** 以便演进。

```json
{
  "version": 1,
  "generated_at": "2026-04-01T12:00:00",
  "tree_rollup": "hex-string",
  "file_count": 42,
  "max_mtime_ns": 1712000000000000000,
  "engine": "notemanager-x.y.z"
}
```

- **version**：摘要格式版本，便于迁移。
- **generated_at**：ISO8601，便于排查；可与 `status.last_build` 接近但不必相等（生成时机略不同也可接受）。
- **file_count**：与 `scan_directory` 规则一致的 `.md/.rst` 数量（排除 `SKIP_DIRS` 等，与现有扫描语义一致）。
- **max_mtime_ns**：所有纳入统计的源文件中，`st_mtime_ns`（或退化为 `st_mtime` 转纳秒）的最大值；用于与 `status.last_build` 做快速比较时的辅助信号。
- **tree_rollup**：整棵源树 rollup 摘要（见下节），**单一字符串**，长度固定（如 64 hex）。

可选扩展（第二阶段）：

- **top_level_dir_nonces**：仅记录第一层子目录的摘要，用于「只在子树内变更」时的剪枝（实现复杂，可作为后续优化）。

## 6. Rollup 摘要算法（建议）

### 6.1 输入

在 **一次深度优先的树遍历** 中，对每个命中的源文件（与 `scan_directory` 过滤规则一致）取：

- 相对路径 `rel_path`（POSIX 风格字符串，保证稳定规范化）；
- `mtime_ns`（优先 `st_mtime_ns`，否则由 `st_mtime` 换算）；
- `size`（字节，`st_size`）。

### 6.2 聚合方式（示例）

将每个文件贡献一行规范化文本，字典序排序后拼接，再对整体做 **SHA-256**（或 BLAKE2/xxHash，实现时权衡依赖与速度）：

```text
line_i = f"{rel_path}\0{mtime_ns}\0{size}\n"
tree_rollup = HEX( SHA256( line_1 + line_2 + ... + line_n ) )
```

**排序**保证与遍历顺序无关；**包含 size** 可在 mtime 被刻意伪造时降低误判「未变」的概率（仍非密码学保证）。

### 6.3 与 `status.json` 的联合判定（快路径）

启动时顺序如下（逻辑）：

1. 若 `status.json` 或 `search_index.json` 缺失 → **必须 full_build**（与现有一致）。
2. 读取 `scan_manifest.json`；若缺失、版本不兼容或解析失败 → **进入完整扫描判定**（即当前 `_need_rebuild_on_startup` 逻辑）。
3. **快路径尝试**（不枚举所有文件）：
   - 读取项目根目录或 `.NoteManager` 的 **单一标量**（见 6.4「根锚点」），若与 manifest 中记录的锚点一致，且 `manifest.file_count` 与 `status.file_count` 一致，且 `manifest.max_mtime_ns` 与上次构建时间窗口相容，则 **推断未变**，跳过 full_build。
4. 若快路径不满足 → 执行 **一次完整遍历** 计算 **live rollup**，与 `manifest.tree_rollup` 比较：
   - 相等 → 跳过 full_build，并可选择 **重写 manifest**（刷新 `generated_at`）；
   - 不等 → full_build，成功后 **写入新的 manifest**。

### 6.4 根锚点（可选优化）

部分文件系统对目录本身提供可变的 `st_mtime`。可定义：

- `root_anchor = f"{root_stat.st_mtime_ns}:{root_stat.st_ino}"`（具体字段以实现时可用性为准）

将 `root_anchor` 存入 manifest。快路径先 `stat(project_root)`，与 manifest 中锚点比较；不一致则 **直接** 进入 live rollup 全量计算，避免假阴性。

> 注意：并非所有平台/文件系统上目录 mtime 都可靠；锚点失败时仅 **降级为全量 rollup**，不影响正确性。

## 7. 更新与失效时机

| 事件 | 行为 |
|------|------|
| `full_build` 成功结束 | 写入/更新 `scan_manifest.json`（与 `status.json` 同一事务顺序：先写构建产物与 status，再写 manifest）。 |
| `update_file` / `remove_file` 等增量构建成功 | 可选增量更新 manifest（维护滚动哈希较难）；**简化实现**可仅在全量构建时更新 manifest，增量阶段只依赖 watcher + 现有逻辑。 |
| 用户手工删除 `.NoteManager` 部分内容 | 缺失文件会触发「必须重建」或「manifest 不匹配」，由现有判定兜底。 |

推荐 **第一版实现**：仅在 `full_build` 完成时 **重写** manifest；启动判定仍用 manifest + 可选全量 rollup 对比，避免为增量路径引入额外复杂度。

## 8. 复杂度与预期收益

- **最坏情况**：与今天相同——一次完整文件枚举 + 可能 full_build。
- **最好情况（manifest 命中且根锚点一致）**：O(1) `stat` + 读小 JSON，显著减少大仓库启动时的目录遍历。
- **中间情况**：一次完整枚举仅用于计算 rollup（不渲染、不建索引），CPU/磁盘仍远小于 `full_build`。

## 9. 与当前代码的衔接点（实现时）

- 将「rollup 计算」与 `scan_directory` **共享同一套过滤规则**（`SKIP_DIRS`、`INCLUDE_EXTENSIONS`），避免摘要与真实扫描语义漂移。
- `_need_rebuild_on_startup()` 中：先尝试 manifest 快路径，失败再调用现有 `scan_directory` 比较逻辑。
- 日志建议区分：`跳过重建（manifest）` / `跳过重建（完整扫描比对）` / `执行重建`。

## 10. 风险与对策

| 风险 | 对策 |
|------|------|
| 哈希碰撞导致误判「未变」 | 以全量扫描 + mtime 比对为最终仲裁；manifest 仅作加速。 |
| 目录 mtime 不可靠 | 根锚点失败则降级全量 rollup。 |
| 跨平台时间精度 | 统一使用纳秒字段；无法获取时文档化降级策略。 |

---

**结论**：快速统计缓存的本质是 **持久化「源树统计摘要」+ 分层判定**：能 O(1) 排除则排除；否则做一次 **无渲染的统计遍历** 计算 rollup；仍不确定再走与今日一致的完整比较或 `full_build`。这样既回应「不要每次启动都全量重建索引」的产品预期，也避免对文件系统做出不现实的承诺。

## 11. 实现状态（代码）

- 模块：`notemanager/scan_manifest.py`（`MANIFEST_VERSION`、`build_manifest_payload`、`write_scan_manifest`、`read_scan_manifest`、`live_payload_and_files`）。
- 落盘路径：`<项目>/.NoteManager/scan_manifest.json`。
- `full_build` 成功写入 `status.json` 之后 **立即** 写入/覆盖 `scan_manifest.json`。
- Daemon 恢复项目时：`notemanager/daemon.py` 中 `_need_rebuild_on_startup()` 先比对实时 rollup 与已存 manifest；**无 manifest 或版本不匹配** 时回退到原先的 `last_build` + `file_count` 判定。
- **未实现**（按本文第 7 节）：增量 `update_file` / `remove_file` 后同步更新 manifest；当前依赖下次启动时 rollup 不一致触发 `full_build` 或依赖 watcher 增量更新（与 manifest 不同步时保守地全量重建）。
